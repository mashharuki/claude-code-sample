# セキュリティ・認証パターン深掘り

セキュリティ図は「何が守られているか」だけでなく「誰が/何を検証しているか」が伝わることが
重要。守りたい対象(データ/API/インフラ)と脅威(不正アクセス/DDoS/内部脅威)を確認してから
テンプレートを選ぶ。

## レイヤー別の防御と対応テンプレート

| レイヤー | 防御の目的 | 主な要素 | 対応テンプレート |
|---|---|---|---|
| エッジ(ネットワーク境界) | DDoS対策、既知の攻撃パターンの遮断 | Shield, WAF, CloudFront | `waf-cdn-edge-security` |
| 認証(Authentication) | 「誰か」を確認する | Cognito, MFA, OIDC/SAML IdP | `zero-trust-identity-auth` |
| 認可(Authorization) | 「何ができるか」を確認する | Lambda Authorizer, IAM Role(最小権限), Policy | `zero-trust-identity-auth` |
| シークレット管理 | 認証情報自体を守る | Secrets Manager, KMS | 両テンプレートに含まれる |
| 検知・監視 | 異常な挙動を発見する | GuardDuty, CloudWatch, 監査ログ | 両テンプレートに含まれる |

## ゼロトラストの図示で意識すること

「ゼロトラスト」は「境界の内側だから安全」という前提を置かない設計原則。図でこれを伝えるには:

- **すべてのリクエストが認証・認可を通過することを矢印で明示する**。「内部ネットワークだから
  検証省略」という経路を作らない。
- **最小権限の原則をIAM Roleのラベルで表現する**(「読み取り専用」「特定リソースのみ」など、
  具体的な権限範囲を書けるとより説得力がある)。
- **多層防御(Defense in Depth)を示す**: WAFで弾く→Authorizerで検証→アプリ側でも入力検証、
  というように1箇所だけに頼らない構成であることが伝わるようにする。

## 認証フロー(OIDC/SAML)を描くときのポイント

1. ユーザー → IdP(Cognito等)への認証(ログイン)
2. IdP → クライアントへのトークン発行(JWT等)
3. クライアント → APIへのリクエスト(トークン添付)
4. API側でのトークン検証(署名検証、有効期限、スコープ確認)— ここを省略しない。
   `zero-trust-identity-auth.drawio` では Lambda Authorizer がこの役割を担い、IdPへの
   JWKS検証を破線で示している。
5. 検証成功後、最小権限のIAM Roleで実際の処理を実行

## よくある誤り

- WAFとShieldを同じ役割として描かない(WAF=アプリケーション層のルールベース防御、
  Shield=ネットワーク/トランスポート層のDDoS対策で役割が異なる)。
- 認証(誰か)と認可(何ができるか)を1つの矢印にまとめて曖昧にしない。分けて描く方が
  レビューする側が抜け漏れに気づきやすい。
- Secrets Managerへの経路を省略し、パスワードやAPIキーがコード内にハードコードされている
  かのような誤解を与える構成にしない。
