# レイアウト・スタイルガイド

「なんとなく雑」に見える図と「実務で人に見せられる」図の差は、ほぼ全てレイアウトの一貫性から
生まれる。内容が正しくても、アイコンの大きさがバラバラだったり余白が不揃いだったりすると
信頼感が下がる。ここでは `scripts/dio.py` が前提にしている規約と、それに沿って描くための
ルールをまとめる。

## 座標とグリッド

- アイコンサイズは **78x78px**(`ICON`定数)に統一する。actor(人型)は 60x70、internetは
  60x60 など例外はあるが、それ以外は揃える。
- 横方向のアイコン間隔は **160〜200px** を目安にする(アイコン78px + ラベル用の余白)。
  詰めすぎるとラベルが隣のアイコンに重なる。
- コンテナの内側パディングは上部60px(ラベル分)、左右30〜40pxを最低確保する。
- 大きな構成(VPC等)は先に外側のコンテナを配置し、内側の要素は**コンテナ基準の相対座標**で
  配置する(draw.ioの仕様: 子要素の x/y は親の左上が原点)。

## コンテナの入れ子で「境界」を表現する

現実のシステムには複数レベルの境界がある。それぞれ視覚的に区別する:

1. **Region**(実線、角丸、太めの枠) — マルチリージョン構成で使う
2. **Availability Zone**(点線、細め) — Region内の物理的な分離
3. **VPC**(AWS4公式のgroup_vpcシェイプ、角に雲マーク)
4. **Subnet**(Public/Private/Isolatedで塗り分け) — VPC内のネットワークセグメント
5. **Security Group / Tenant Boundary** — 論理的なアクセス境界

境界を省略すると「どこまでが信頼境界か」が伝わらず、レビューする側が可用性やセキュリティを
評価しづらい図になる。可用性・DR・マルチテナントを扱う図では特に、この入れ子を省略しない。

## 色のルール

- 色は**装飾ではなく意味**を持たせる。AWSアイコンは公式カテゴリ色(`aws-icon-guide.md`参照)
  に従う。汎用シェイプは以下の慣習に統一する:
  - 青(`box`) = アプリケーション/API層
  - 紫(`box_purple`) = AI/ML処理
  - オレンジ(`box_orange`) = 非中央集権的なノード群、イベント/非同期処理
  - グレー(`box_gray`) = 横断的関心事(監視・監査・ポリシー)
  - オレンジ系の枠(`tenant`) = マルチテナント境界
- 1枚の図で使う色数は6〜8色程度に抑える。多用すると意味が薄れる。

## 矢印(エッジ)のルール

- **ラベルのない矢印を作らない**。何が流れるか(プロトコル、データ種別、操作)を一言添える。
  例:「HTTPS」「非同期」「同期レプリケーション」「マルチシグ承認後にmint」。
- **実線 = 主経路・同期処理**、**破線(`dashed=True`) = 副次経路・非同期・監視・バックアップ・
  レプリケーション**。この区別があると、読み手は「本番トラフィックの通り道」と「裏側の仕組み」を
  瞬時に見分けられる。
- 重要な経路(フェイルオーバー、承認フロー等)を強調したい場合は `EDGE_STYLE_BOLD`
  (太線・濃色)を使う。
- 経路が交差して見づらい場合は、`mcp__drawio__open_drawio_xml` の `routing="libavoid"`
  オプションで自動的にきれいな直角配線に補正できる(座標はそのまま、配線だけ最適化される)。

## タイトルと注釈

- 図の左上に `Diagram.text()` でタイトルを必ず入れる(`fontSize=15, fontStyle=1`)。
  タイトルがないと、複数の図をまとめて共有したときにどれがどれか分からなくなる。
- 補足説明が必要な箇所(例:「Pilot Light: 最小構成で待機」)は、ラベルやコンテナタイトルに
  カッコ書きで含める。別の凡例ボックスを作るより、その場に書いた方が読み手の視線移動が減る。

## 要素数が多くなってきたら

1枚の図に20個を超える要素を詰め込むと、どれだけレイアウトを整えても読みにくくなる。
その場合の選択肢(優先順):

1. **観点で図を分ける** — 例:「ネットワーク構成図」と「データフロー図」を別ページにする。
   `mcp__drawio__list_pages` / `set_page` で1ファイル内に複数ページを追加できる。
2. **抽象度を上げる** — 個々のLambda関数を列挙せず「Lambda群(N個)」のように集約する。
3. **主要経路だけを実線、それ以外を薄いグレーの補助線にする** — 全部を同列に強調しない。

## コンテナに接続する矢印はentry/exitポイントを明示する

AWS4のグループシェイプ・汎用コンテナは `verticalAlign=top;align=left;spacingLeft=12` で
左上にラベルを表示する。コンテナ自体やその子要素に矢印を接続すると、draw.ioの自動配線が
ラベルのすぐ近く(コンテナ上端の左寄り)に接続点を選びがちで、線とラベル文字が重なって
読みにくくなることがある(`landing-zone-multi-account.drawio` の初版で実際に発生し、修正した)。

複数の矢印が同じコンテナや隣接コンテナに集中する図(統治構造、ネットワークのハブ&スポーク等)
では、`mxCell` の style に `entryX`/`entryY`(着地点)や `exitX`/`exitY`(出発点)を明示して、
ラベル領域(左上)を避けるようにする:

```python
# コンテナの上端中央に接続する(左上のラベルを避ける)
d.edge(src, container, "ラベル", style=EDGE_STYLE + "entryX=0.5;entryY=0;entryDx=0;entryDy=0;")

# 隣接するコンテナの子要素同士を、上端ではなく側面の中〜下寄りで接続する
d.edge(a, b, "ラベル", style=EDGE_STYLE + "exitX=0;exitY=0.3;exitDx=0;exitDy=0;entryX=1;entryY=0.3;entryDx=0;entryDy=0;")
```

複数の矢印が同じコンテナに入る場合は、`entryY`(または`entryX`)の値を0.3/0.7のようにずらして
分散させると、線同士が重ならず追いやすくなる。この対応が必要かどうかは、`open_drawio_xml`で
実際に開いて目視確認するまでは判断できないことが多い — 「コンテナへの矢印が3本以上集中する」
「隣接コンテナの子要素同士を繋ぐ」場合は、最初から entry/exit を明示しておくと手戻りが少ない。
