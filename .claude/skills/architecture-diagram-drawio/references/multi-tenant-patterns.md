# マルチテナントパターン深掘り (Silo / Pool / Bridge)

マルチテナントSaaSの分離モデルは大きく3種類あり、テナントごとの要件(分離度、コスト、
運用の複雑さ)によって選択が変わる。「マルチテナントの図が欲しい」と言われたら、
まずどのモデルを想定しているか(または比較したいのか)を確認する。

## 3つのモデル

| モデル | 分離の単位 | コスト効率 | 分離レベル | 対応テンプレート |
|---|---|---|---|---|
| **Silo(サイロ)** | テナントごとに専用スタック(コンピュート/DB/ストレージを完全分離) | 低い(テナント数分のインフラコスト) | 最高(ノイジーネイバー問題なし、テナント間のデータ漏洩リスクが構造的に低い) | `multi-tenant-saas-silo-model` |
| **Pool(プール)** | 全テナントが同一インフラを共有し、`tenant_id` で論理分離 | 高い(スケールメリットが効く) | アプリケーションロジックに依存(バグがあれば漏洩しうる) | `multi-tenant-saas-pool-model` |
| **Bridge(ブリッジ)** | コンピュートは共有、DBはテナントごとに分離 など、レイヤーごとに異なるモデルを併用 | 中間 | 中間 | 上記2テンプレートの要素を組み合わせて表現する |

## 図に必ず含めるべき要素

### Poolモデル
- **テナント識別の伝播経路**: APIゲートウェイ等でリクエストにテナントコンテキストを付与する
  箇所を明示する(`multi-tenant-saas-pool-model.drawio` では API Gateway のラベルに
  「テナントコンテキスト付与」と明記)。
- **論理分離のキー**: DynamoDBのパーティションキーが `tenant_id` であることなど、
  「どうやって他テナントのデータと混ざらないようにしているか」をラベルで示す。
  これが図示されていないと、Poolモデルのレビューで最も懸念される「データ漏洩リスク」に
  対する説明が欠落する。
- **テナント別の可観測性**: CloudWatchのメトリクスをテナント別に分けられるかどうかは
  運用上重要なので、該当する場合は明記する。

### Siloモデル
- **ルーティングの分岐点**: サブドメイン(`tenant.example.com`)やパスベースでどうやって
  テナント専用スタックに振り分けるかを図の入口で示す(`multi-tenant-saas-silo-model.drawio`
  では Route 53 が担当)。
- **テナントごとの暗号鍵**: KMSのCMKをテナント別に分けている場合はそれも分離の一部として
  明示する(コンプライアンス要件で「テナントごとに鍵を分離」を求められるケースがあるため)。

## よくある誤り

- Poolモデルで「共有」であることだけ描いて、テナント分離の仕組み(どこでtenant_idを
  チェックしているか)を省略しない。これがないと「本当に安全に分離されているのか」が
  伝わらない図になる。
- Siloモデルで「テナントごとに完全分離」と言いながら、共有コンポーネント(例えば
  認証基盤や監視基盤)がある場合はそれも正直に描く(完全な100%分離は稀で、多くの実装は
  一部を共有している)。
- コスト比較を求められた場合、Silo=高コスト/高分離、Pool=低コスト/要注意、という
  トレードオフを図の注釈やタイトルで一言添えると、意思決定に役立つ図になる。
